# Java Blueprints — как это работает и как это показать

Документ для команды: устройство продукта простыми словами, путь пользователя от входа на сайт до доказанного
результата, сценарий демо на 5–7 минут с репликами и ответы на вероятные вопросы жюри.

---

## 1. Что это одной фразой

**Загружаешь Java-монолит — видишь его как схему, находишь, где он медленный и запутанный, меняешь логику прямо на
схеме, а система сама доказывает запуском в изолированном Docker, что программа ведёт себя так же, как до правки.**

Кейс требует ровно этот путь: Монолит → Граф → Диагноз → Улучшение → Тесты (слайды 3 и 10).

## 2. Как это устроено внутри (30 секунд на слайд)

```
Браузер (Next.js, React Flow)
   │  рисует графы, редактор кода, панели
   ▼
API (Rust/Axum) ── хранит проекты и ревизии, ничего не знает о синтаксисе Java
   │  запускает                              │  запускает
   ▼                                         ▼
Анализатор (Java 21 + Eclipse JDT)          Раннер (Docker, JDK 21)
  AST, граф потока (CFG), Big O,              компилирует и запускает ревизию:
  находки, переписывание кода                 без сети, read-only, лимиты CPU/памяти/времени
```

Ключевые принципы, которые стоит проговорить:

- **Java понимает только настоящий компилятор Java** (Eclipse JDT, тот же, что в IDE Eclipse). Мы не пишем свой
  «парсер на регулярках»: типы, вызовы и перегрузки разрешаются как в IDE.
- **Каждая правка — новая ревизия.** Код переписывается через ASTRewrite (правка синтаксического дерева), результат
  заново компилируется и анализируется; если правка ломает метод — она отклоняется с причиной. Любую ревизию можно
  сравнить с любой и откатить.
- **Загруженный код исполняется только в одноразовом Docker-контейнере.** Никогда на сервере.
- **Ничего не выдумываем.** Нет Docker — честная ошибка «раннер недоступен», а не зелёная галочка. Ускорение — только
  измеренное, со статистикой; оценка Big O — с допущениями и уровнем уверенности.

## 3. Путь пользователя end-to-end (что нажимать)

Демо-файл: `apps/api/tests/fixtures/demo/Main.java` — консольный «склад заказов», 819 строк, в одном файле:
парсинг ввода → анализ → оптимизация → вывод, с типичными дефектами производительности.

| Шаг | Что делает пользователь | Что видит |
|---|---|---|
| 1. Загрузка | На главной перетаскивает `.java` или ZIP-проект | Проект открывается, сверху — полоса шагов «Анализ → Оптимизация → Проверка → Замер → Разбор → Отчёт» |
| 2. Обзор | Ничего — анализ идёт сам | **Граф проекта**: классы и связи. Справа **«Проблемы»**: что не так, почему, что делать. Слева дерево файлов и методов |
| 3. Метод | Двойной клик по классу или выбор метода → вкладка **CFG** | **Блок-схема метода**: условия — ромбы с «Да/Нет», циклы — фиолетовые, возвраты — зелёные; проблемные узлы помечены красным. Клик по узлу подсвечивает строку кода |
| 4. Сложность | Вкладка **«Правка»** справа | **O(n + m·k)** и расшифровка: что такое n, m, k (какие коллекции), как читать формулу («вложенные циклы — произведение»), **какие циклы по строкам её дают** |
| 5. Оптимизация | Вкладка **«Советы»** → правило → **«Предпросмотр diff»** | Большое окно: diff «было/стало», **допущения с галочками** (например, «ключ не null»), оценка «O(n²) → O(n + m + k)». «Применить» создаёт новую ревизию |
| 6. Автопроверка | Ничего | В шапке сама загорается **«Поведение сохранено · 6/6»**: сценарии были предложены по коду (команды, которые программа сравнивает с вводом), и REV 1 сравнилась с новой ревизией в Docker |
| 7. Правка руками | Тащит блок из палитры «Блоки» на оператор графа / тащит оператор на другой | Предпросмотр вставки или переноса → «Применить» → новая ревизия → снова автопроверка |
| 8. Запуск | Кнопка **«Запуск»**, ввод в stdin | Вывод программы и **путь выполнения на графе**: выполненные узлы обведены и подписаны «×N», невыполненные приглушены |
| 9. Замер | Иконка «Бенчмарк» | Время до/после на разных размерах входа, со статистикой; «ускорение ×N» только если оно значимо |
| 10. Разбор монолита | «Разбор монолита» | Вынести вложенные классы (`InputParser`, `OrderAnalyzer`, `DataOptimizer`…) в отдельные файлы — как на слайде 6; проверка поведения после |
| 11. Отчёт и экспорт | «Отчёт», «Экспорт Java» | Markdown-отчёт о том, что найдено, что изменено и чем доказано; архив исходников новой ревизии |

**Как разобраться новому пользователю:** идти по полосе шагов сверху слева направо — каждый шаг подсвечивается, когда
к нему можно перейти, и ведёт в нужную панель. Любой узел графа кликабелен (показывает код), любая проблема —
кнопкой «Показать на графе».

## 4. Речь для презентации (5–7 минут)

> Реплики — ориентир, не текст для чтения. В скобках — что в этот момент на экране.

**0:00 — Проблема (без экрана или титул).**
«Представьте, вам дали тысячу строк чужого Java-кода в одном файле и сказали: ускорь и ничего не сломай. Сложность
не в том, чтобы поменять код, а в двух вопросах: *где* он медленный и *как доказать*, что после правки он работает так
же. Мы сделали инструмент, который отвечает на оба.»

**0:40 — Загрузка и граф (загружаем `Main.java`).**
«Загружаем монолит. Анализатор — это Eclipse JDT, настоящий компилятор Java, а не регулярные выражения, поэтому он
понимает типы и вызовы как IDE. Сразу видим граф проекта: 17 типов, кто от кого зависит. Справа — найденные проблемы
с объяснением: что не так, почему это плохо и что делать.»

**1:30 — Блок-схема и диагноз (двойной клик → CFG → «Правка»).**
«Проваливаемся в метод — это его блок-схема: ромбы — условия, фиолетовые — циклы. Красным помечено место проблемы.
Это ровно пример со слайда 5 кейса: цикл по товарам внутри цикла по товарам — O(n²). Мы не просто пишем O(n²):
объясняем, что n — это число элементов в `items`, что вложенные циклы дают произведение, вдвое больше данных — в
четыре раза дольше, и показываем, какой цикл на какой строке это даёт.»

**2:30 — Оптимизация (Советы → предпросмотр → галочки → применить).**
«Инструмент предлагает исправление: построить индекс HashMap. Перед применением — точный diff и допущения, которые
нужно подтвердить: например, что ключ не null. Мы не прячем риски: если допущение не выполняется, оптимизация была бы
некорректной, и это решение человека. Применяем — получаем новую ревизию.»

**3:20 — Доказательство (бейдж в шапке, затем вкладка «Проверка»).**
«А теперь главное — ключевой контракт кейса. Проверка запустилась сама: обе версии скомпилированы и запущены в
одноразовых Docker-контейнерах без сети на одних и тех же сценариях ввода, сценарии мы предложили по коду. Сравнили
вывод, ошибки и код выхода побайтово — совпало. Мы честно пишем, что это доказательство для этих сценариев, а не для
всех входов, и предупреждаем, если сценарий не доходит до изменённого кода.»

**4:10 — Замер (Бенчмарк).**
«Ускорение не рисуем — измеряем. На размере 1200 элементов новая версия быстрее в ~2,7 раза, со статистическим
тестом и доверительным интервалом. Если разница незначима — так и пишем.»

**4:50 — Визуальное редактирование и запуск (перетащить блок, затем «Запуск»).**
«Логику можно менять прямо на схеме: перетаскиваем блок из палитры на оператор — предпросмотр — применить. Код
перегенерирован, граф перестроен, проверка снова сама подтвердила поведение. А кнопка «Запуск» показывает путь
выполнения: какие узлы реально выполнились и сколько раз.»

**5:40 — Разбор монолита (опционально).**
«И при необходимости — слайд 6: выносим ответственности в отдельные файлы — парсер, анализатор, оптимизатор — и снова
проверяем поведение.»

**6:10 — Итог.**
«Полный путь кейса: монолит → граф → диагноз → улучшение → автоматическая проверка. Под капотом — компилятор Java,
изоляция в Docker, больше 350 автотестов и CI на каждый коммит, в том числе браузерные тесты против настоящего
бэкенда. Спасибо.»

## 5. Вопросы жюри и короткие ответы

- **«Big O — это же эвристика?»** — Статическая оценка сверху по модели стоимости, с уровнем уверенности и списком
  допущений; там, где модели нет, честно пишем `unknown`. Реальный эффект подтверждаем замером.
- **«Почему проверка не доказывает эквивалентность?»** — Полная эквивалентность программ неразрешима в общем случае.
  Мы сравниваем наблюдаемое поведение на сценариях, предлагаем сценарии по коду, повторяем запуски, чтобы отличить
  случайность от изменения, и предупреждаем, если сценарий не доходит до правки.
- **«Что будет на нашем монолите?»** — Поддерживается Java 8–21, обязательный scope слайда 7 покрыт тестами
  (`JavaScopeChecklistTest`, по тесту на каждый пункт). Находки качества кода (длинный метод, вложенность,
  дублирование) работают на любом коде; оптимизации применяются только там, где доказаны предусловия.
- **«Безопасно ли запускать чужой код?»** — Только в одноразовом контейнере: без сети, read-only, лимиты CPU, памяти,
  процессов и времени. На сервере API код никогда не исполняется.
- **«Чем вы лучше простого рефакторинга в IDE?»** — IDE не объясняет сложность, не предлагает алгоритмическую
  оптимизацию с допущениями и не доказывает запуском, что поведение сохранилось. У нас это один связанный путь.
- **«Что не успели?»** — Пошагового отладчика нет (есть трасса всего запуска на графе); публичного сервера нет —
  запуск одной командой `docker compose up --build`; разбор монолита механический (по типам и префиксам методов),
  а не «понимание смысла».

## 6. Чек-лист перед выступлением

1. `docker compose up -d --build`, открыть `http://localhost:3001`, жёсткое обновление (Cmd+Shift+R).
2. Прогнать демо один раз целиком до выступления (контейнеры прогреваются, первая проверка дольше).
3. Держать открытым второй вкладкой уже прогнанный проект на случай сбоя сети или Docker.
4. Шрифт браузера 110–125 %, чтобы было видно с проектора; закрыть лишние панели (низ — «Свернуть»).
5. Запасные скриншоты: `docs/screenshots/`.
