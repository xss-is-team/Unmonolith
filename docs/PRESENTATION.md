# Java Blueprints — как это работает и как это показать

Документ для команды: устройство продукта простыми словами, путь пользователя от входа на сайт до доказанного
результата, сценарий демо на 5–7 минут с репликами и ответы на вероятные вопросы жюри.

---

## 1. Что это одной фразой

**Загружаешь Java-монолит — видишь его как схему, находишь, где он медленный и запутанный, меняешь логику прямо на
схеме, а система сама доказывает запуском в изолированном Docker, что программа ведёт себя так же, как до правки.**

Кейс требует ровно этот путь: Монолит → Граф → Диагноз → Улучшение → Тесты (слайды 3 и 10).

## 2. Как это устроено внутри (30 секунд на слайд)

```
Браузер (Next.js, React Flow)
   │  рисует графы, редактор кода, панели
   ▼
API (Rust/Axum) ── хранит проекты и ревизии, ничего не знает о синтаксисе Java
   │  запускает                              │  запускает
   ▼                                         ▼
Анализатор (Java 21 + Eclipse JDT)          Раннер (Docker, JDK 21)
  AST, граф потока (CFG), Big O,              компилирует и запускает ревизию:
  находки, переписывание кода                 без сети, read-only, лимиты CPU/памяти/времени
```

Ключевые принципы, которые стоит проговорить:

- **Java понимает только настоящий компилятор Java** (Eclipse JDT, тот же, что в IDE Eclipse). Мы не пишем свой
  «парсер на регулярках»: типы, вызовы и перегрузки разрешаются как в IDE.
- **Каждая правка — новая ревизия.** Код переписывается через ASTRewrite (правка синтаксического дерева), результат
  заново компилируется и анализируется; если правка ломает метод — она отклоняется с причиной. Любую ревизию можно
  сравнить с любой и откатить.
- **Загруженный код исполняется только в одноразовом Docker-контейнере.** Никогда на сервере.
- **Ничего не выдумываем.** Нет Docker — честная ошибка «раннер недоступен», а не зелёная галочка. Ускорение — только
  измеренное, со статистикой; оценка Big O — с допущениями и уровнем уверенности.

## 2a. Big O под капотом: как анализатор получает формулу

Это главный вопрос жюри. Отвечать надо так: **оценку выводит программа по строгим правилам, а не угадывает модель.
Каждую букву формулы можно проследить до конкретного цикла в коде.** Код: `apps/parser/.../ComplexityAnalyzer.java`,
движок `jdt-static-cost-model/2`.

### Шаг 1. Компилятор Java строит дерево с типами

Eclipse JDT разбирает исходник в AST и **разрешает привязки**: про каждый вызов известно, какой метод какого класса
вызывается (`ArrayList.contains`, `HashMap.get` или метод проекта), про каждую переменную известны её тип и
объявление. Поэтому `items.contains(x)` у `List` и у `Set` — для нас разные операции. Регулярное выражение или
нейросеть по тексту различают их только по догадке.

### Шаг 2. Стоимость — это многочлен от «переменных размера»

Стоимость любого куска кода хранится как сумма одночленов от **переменных размера**: число элементов коллекции
(`items`), значение int-границы цикла, число строк на входе. У каждой переменной есть степень и степень логарифма.
Пример: `n²`, `n·m`, `n log n`. Правила алгебры такие:

| Конструкция | Правило |
|---|---|
| операторы подряд, `if`/`else`, `switch` | **сложение**; слагаемое, которое покрывается другим, отбрасывается (`n² + n → n²`) |
| цикл | стоимость тела **умножается** на число итераций |
| вызов метода JDK | берётся из **таблицы моделей**: `ArrayList.get` O(1), `List.contains`/`indexOf` O(n), `HashMap.get` O(1) в среднем, `TreeMap.get` O(log n), `PriorityQueue.add` O(log n), `LinkedList.get` O(n)… |
| вызов метода проекта | этот метод **анализируется так же** (до 8 уровней вглубь, с защитой от циклов), его оценка переписывается в размеры переданных аргументов; через интерфейс — анализируются **все реализации** в проекте |
| всё, что нельзя обосновать | **`unknown` с причиной** вместо выдуманного числа |

### Шаг 3. Число итераций цикла распознаётся по форме, а не по названию

- `for (Item a : items)` → `n` = число элементов `items` (и `keySet()`/`values()`/`entrySet()` — по самой карте);
- `for (i = 0; i < n; i++)` → линейно, если счётчик меняется **ровно в одном месте** шагом-константой и граница не
  меняется внутри цикла; `i *= 2` или `n /= 2` → `log n`;
- `while (lo <= hi)` с `mid = (lo + hi) / 2` и обновлениями `lo = mid + 1` / `hi = mid - 1` на каждом пути →
  бинарный поиск, `log n` (допущение «нет переполнения lo + hi» показывается явно);
- алгоритм Евклида (`a % b`) → `log`;
- `while (scanner.hasNextLine())` → число строк ввода;
- прямая рекурсия решается как рекуррентное соотношение: `f(n-1)` один раз → `O(n)`, `f(n/2)` → `O(log n)`,
  два вызова `f(n-1)`, `f(n-2)` → `O(2^n)` с пометкой «это верхняя граница, Фибоначчи на деле Θ(1.618ⁿ)».
  Без проверки базового случая перед рекурсивным вызовом — `unknown`;
- константная граница (`i < 10`) → O(1), и это тоже пишется в допущениях.

Если счётчик меняется в двух местах, внутри есть `continue`, который может пропустить шаг, или граница растёт внутри
цикла, анализатор **отказывается** и пишет почему, например: *«Счётчик 'i' меняется ещё и в теле цикла»*.

### Шаг 4. Уверенность и допущения

- `high` — всё доказано правилами (циклы по коллекциям, точные модели);
- `medium` — опирается на допущение (хеш O(1) в среднем, `ArrayList` с произвольным доступом, строки короткие, все
  реализации интерфейса видны в проекте);
- `low` — `unknown`.

Каждое допущение выводится в интерфейс. Буквы формулы расшифрованы: *«n — число элементов в `items`»*.

### Шаг 5. Находки — это закономерности на тех же данных

- **повторный линейный поиск**: внутренний цикл по коллекции ищет элемент по равенству с переменной внешнего цикла →
  `repeated_collection_scan`, рекомендация «индекс HashMap»;
- **вложенный перебор одной коллекции** → `nested_collection_iteration`, O(n²);
- **`s += x` в цикле** → копирование всей строки на каждом шаге → `StringBuilder`;
- качество кода: длинный метод (>60 строк), вложенность ≥4, >5 параметров, дублирование блоков.

Каждая находка привязана к строке и к узлам CFG, поэтому есть «Показать на графе».

### Шаг 6. Оптимизация применяется, только если доказаны предусловия

Например, для `HashMap`-индекса в примере со слайда 5 анализатор проверяет: коллекция не меняется в цикле, ключ
сравнивается через `equals` или `==`, вызываемые методы (`merge(a, b)`) **транзитивно не трогают** коллекцию и поля,
из которых берётся ключ. Если что-то не доказать, правило не предлагается или ставит допущение с галочкой, которую
подтверждает человек.

### Шаг 7. Оценку проверяет реальность

Статика говорит, **как растёт** время. «Бенчмарк» запускает обе версии в Docker на нескольких размерах входа и
показывает, растёт ли время так, как предсказано, и есть ли значимое ускорение (тест Манна-Уитни,
bootstrap-интервал). Кейс прямо требует: *«Диагноз должен быть проверяемым, а не только красивым»* (слайд 5).

### Пример на 30 секунд (слайд 5)

```java
for (Item a : items)            // n раз      (n = число элементов items)
  for (Item b : items)          //   × n раз
    if (a.id().equals(b.id()))  //     O(1): String.equals, короткая строка — допущение
      merge(a, b);              //     O(1): merge проанализирован, циклов нет
```

`n · n · 1 = O(n²)`, уверенность `medium` (из-за допущения о строках). Находка: повторный поиск по `items`. Правило
`nested_scan_to_hashmap`: один проход строит `Map<id, Item>`, второй — поиск за O(1) → **O(n)**. Применение →
новая ревизия → автопроверка в Docker → бенчмарк подтверждает ускорение.

### Что мы честно не умеем

- память (space complexity) не оцениваем;
- рекурсию сложнее одного параметра-счётчика (quicksort, обход дерева) честно помечаем `unknown`;
- стримы и пользовательские дженерики → `unknown`;
- модель стоимости JDK описывает типичные реализации (это указано в допущениях).

Как это говорить: *«Мы предпочитаем сказать "не знаю, вот почему", чем выдать красивую, но непроверяемую цифру».*

## 2b. Мы и решения на нейросети

Про другие команды мы знаем одно: в некоторых решениях анализ сложности делает нейросеть (LLM). **Не нападать на них
в лоб.** Сформулировать различие и дать жюри критерий, по которому оно увидит разницу само.

| Вопрос жюри | Анализ нейросетью | Java Blueprints |
|---|---|---|
| Откуда взялась O(n²)? | «модель так ответила»; объяснение сгенерировано и может не совпадать с кодом | цепочка правил: этот цикл — `n`, этот — `× n`; каждая буква привязана к строке |
| Тот же код дважды — тот же ответ? | не гарантировано (температура, версия модели) | детерминированно, один и тот же JSON |
| Что, если не уверена? | обычно всё равно даёт ответ (галлюцинация) | `unknown` + причина + уровень уверенности |
| `List.contains` или `Set.contains`? | по тексту и догадке | по разрешённому типу из компилятора |
| Код уходит наружу? | часто во внешний API | никуда: анализатор локальный, код исполняется только в Docker без сети |
| Скорость и цена | секунды и деньги за запрос, лимиты | миллисекунды на метод, бесплатно, офлайн |
| Покрыто тестами? | сложно тестировать вероятностный вывод | 230 тестов парсера, в т. ч. эталонный набор `ComplexityBenchmarkTest`: O(1), O(n), O(n·m), O(log n), бинарный поиск, Фибоначчи O(2ⁿ), quicksort → `unknown` |
| Правка кода | LLM переписывает текст, может сломать | ASTRewrite + перекомпиляция + сравнение поведения в Docker |

Мы также **проверили академические инструменты** анализа стоимости для Java (AProVE, COSTA) и отказались от них:
AProVE на байткоде доказывает только завершимость, без оценки O(...), и думает от секунд до минут; COSTA доступен
только как веб-форма (`docs/COMPLEXITY_ENGINE.md`). Поэтому свой движок — осознанное решение, а не «не успели
подключить готовое».

**Где нейросеть уместна** (если спросят «а почему без ИИ?»): чтобы пересказать уже доказанный результат человеческим
языком или предложить имя для вынесенного метода. Но не как источник правды о сложности и не для правки кода без
проверки. У нас источник правды — компилятор и запуск.

**Вопрос, который стоит подбросить жюри** (корректно, без названий команд): *«Попросите любое решение объяснить, откуда
взялась каждая буква в O(...), и запустить анализ того же кода дважды».*

## 3. Путь пользователя end-to-end (что нажимать)

Демо-файл: `apps/api/tests/fixtures/demo/Main.java` — консольный «склад заказов», 819 строк, в одном файле:
парсинг ввода → анализ → оптимизация → вывод, с типичными дефектами производительности.

| Шаг | Что делает пользователь | Что видит |
|---|---|---|
| 1. Загрузка | На главной перетаскивает `.java` или ZIP-проект | Проект открывается, сверху — полоса шагов «Анализ → Оптимизация → Проверка → Замер → Разбор → Отчёт» |
| 2. Обзор | Ничего — анализ идёт сам | **Граф проекта**: классы и связи. Справа **«Проблемы»**: что не так, почему, что делать. Слева дерево файлов и методов |
| 3. Метод | Двойной клик по классу или выбор метода → вкладка **CFG** | **Блок-схема метода**: условия — ромбы с «Да/Нет», циклы — фиолетовые, возвраты — зелёные; проблемные узлы помечены красным. Клик по узлу подсвечивает строку кода |
| 4. Сложность | Вкладка **«Правка»** справа | **O(n + m·k)** и расшифровка: что такое n, m, k (какие коллекции), как читать формулу («вложенные циклы — произведение»), **какие циклы по строкам её дают** |
| 5. Оптимизация | Вкладка **«Советы»** → правило → **«Предпросмотр diff»** | Большое окно: diff «было/стало», **допущения с галочками** (например, «ключ не null»), оценка «O(n²) → O(n + m + k)». «Применить» создаёт новую ревизию |
| 6. Автопроверка | Ничего | В шапке сама загорается **«Поведение сохранено · 6/6»**: сценарии были предложены по коду (команды, которые программа сравнивает с вводом), и REV 1 сравнилась с новой ревизией в Docker |
| 7. Правка руками | Тащит блок из палитры «Блоки» на оператор графа / тащит оператор на другой | Предпросмотр вставки или переноса → «Применить» → новая ревизия → снова автопроверка |
| 8. Запуск | Кнопка **«Запуск»**, ввод в stdin | Вывод программы и **путь выполнения на графе**: выполненные узлы обведены и подписаны «×N», невыполненные приглушены |
| 9. Замер | Иконка «Бенчмарк» | Время до/после на разных размерах входа, со статистикой; «ускорение ×N» только если оно значимо |
| 10. Разбор монолита | «Разбор монолита» | Вынести вложенные классы (`InputParser`, `OrderAnalyzer`, `DataOptimizer`…) в отдельные файлы — как на слайде 6; проверка поведения после |
| 11. Отчёт и экспорт | «Отчёт», «Экспорт Java» | Markdown-отчёт о том, что найдено, что изменено и чем доказано; архив исходников новой ревизии |

**Как разобраться новому пользователю:** идти по полосе шагов сверху слева направо — каждый шаг подсвечивается, когда
к нему можно перейти, и ведёт в нужную панель. Любой узел графа кликабелен (показывает код), любая проблема —
кнопкой «Показать на графе».

**Слайд 4 — диагностика и Big O (60 с). Главный слайд.**
«Сначала о том, как мы читаем код. Анализатор построен на Eclipse JDT, это компилятор из IDE Eclipse. Он не
читает текст, а разбирает его: строит синтаксическое дерево и разрешает типы. Мы знаем, что `items` — это
`ArrayList`, а `contains` здесь стоит O(n), а не O(1), как у `HashSet`. Из дерева строим блок-схему каждого метода
и граф связей проекта.

Big O не угадывается, он выводится по правилам, как в учебнике по алгоритмам. Стоимость — это многочлен. Операторы
подряд складываются, цикл умножает стоимость тела на число итераций. Число итераций определяется по форме цикла:
перебор коллекции — n, деление пополам — log n, бинарный поиск, а рекурсия решается как рекуррентное соотношение.
Стоимость методов JDK берётся из таблицы, методы проекта анализируются вглубь, интерфейсы — по всем реализациям.
Поэтому каждая буква формулы ведёт к своему циклу и строке.

Если доказать нельзя, мы пишем "не знаю" и причину. В кейсе сказано: диагноз должен быть проверяемым, а не только
красивым. Нейросеть даст ответ всегда, но не объяснит, откуда он, а на тот же код может ответить иначе. У нас
результат детерминирован, работает офлайн за миллисекунды, и его подтверждает замер.

Ошибки находятся на той же модели. Внутренний цикл ищет элемент по ключу из внешнего — повторный линейный поиск,
O(n²), рецепт "индекс HashMap". Склейка строки в цикле — StringBuilder. Плюс качество кода: длинные методы, глубокая
вложенность, дублирование. Исправление применяется, только если анализатор доказал условия: например, что
вызываемые методы не меняют коллекцию. Что доказать нельзя, показывается как допущение, его подтверждает человек.»

## 4. Речь для презентации (5–7 минут)

же. Мы сделали инструмент, который отвечает на оба.»

**0:40 — Загрузка и граф (загружаем `Main.java`).**
«Загружаем монолит. Анализатор — это Eclipse JDT, настоящий компилятор Java, а не регулярные выражения, поэтому он

**1:30 — Блок-схема и диагноз (двойной клик → CFG → «Правка»).**
«Проваливаемся в метод — это его блок-схема: ромбы — условия, фиолетовые — циклы. Красным помечено место проблемы.
Это ровно пример со слайда 5 кейса: цикл по товарам внутри цикла по товарам — O(n²). Мы не просто пишем O(n²):
объясняем, что n — это число элементов в `items`, что вложенные циклы дают произведение, вдвое больше данных — в
четыре раза дольше, и показываем, какой цикл на какой строке это даёт.»

**2:00 — Как получается Big O (держать открытой панель «Откуда берётся»).**
«Важно, откуда эта цифра. Её не угадывает нейросеть, её выводит анализатор по правилам, как в учебнике по
алгоритмам. Компилятор Java знает тип каждой переменной и какой метод вызывается. Стоимость считается как многочлен:
операторы подряд складываются, цикл умножает стоимость тела на число итераций. Число итераций мы распознаём по форме
цикла: перебор коллекции — n, счётчик с шагом — n, деление пополам — log n, бинарный поиск, рекурсия решается как
рекуррентное соотношение. Стоимость стандартных методов берётся из таблицы: `contains` у списка — O(n), у `HashSet` —
O(1). Методы проекта анализируются так же, вглубь. Поэтому каждая буква формулы кликабельна и ведёт к своему циклу.

## 5. Вопросы жюри и короткие ответы

- **«Big O — это же эвристика?»** — Статическая оценка сверху по модели стоимости, с уровнем уверенности и списком
  допущений; там, где модели нет, честно пишем `unknown`. Реальный эффект подтверждаем замером.
- **«Почему не нейросеть?»** — Нейросеть может пересказать результат, но не доказать его: ответ не воспроизводится,
  объяснение не обязано совпадать с кодом, код уходит во внешний сервис. У нас каждая буква O(...) выводится из
  конкретного цикла, результат один и тот же при каждом запуске, и его подтверждает замер.
- **«Сколько процентов методов вы не смогли оценить?»** — На эталонном монолите `Organizer.java` 22 из 98 методов
  `unknown`, на демо-файле 2 из 65. Это методы со стримами, сложной рекурсией или вызовами без модели, и для каждого
  указана причина.
- **«Покажите, что оценка не выдумана»** — Открыть «Откуда берётся»: клик по циклу подсвечивает строку; затем
  «Бенчмарк» показывает рост времени на разных размерах входа.
- **«Почему проверка не доказывает эквивалентность?»** — Полная эквивалентность программ неразрешима в общем случае.
  Мы сравниваем наблюдаемое поведение на сценариях, предлагаем сценарии по коду, повторяем запуски, чтобы отличить
  случайность от изменения, и предупреждаем, если сценарий не доходит до правки.
- **«Что будет на нашем монолите?»** — Поддерживается Java 8–21, обязательный scope слайда 7 покрыт тестами
  (`JavaScopeChecklistTest`, по тесту на каждый пункт). Находки качества кода (длинный метод, вложенность,
  дублирование) работают на любом коде; оптимизации применяются только там, где доказаны предусловия.
- **«Безопасно ли запускать чужой код?»** — Только в одноразовом контейнере: без сети, read-only, лимиты CPU, памяти,
  процессов и времени. На сервере API код никогда не исполняется.
- **«Чем вы лучше простого рефакторинга в IDE?»** — IDE не объясняет сложность, не предлагает алгоритмическую
  оптимизацию с допущениями и не доказывает запуском, что поведение сохранилось. У нас это один связанный путь.
- **«Что не успели?»** — Пошагового отладчика нет (есть трасса всего запуска на графе); публичного сервера нет —
  запуск одной командой `docker compose up --build`; разбор монолита механический (по типам и префиксам методов),
  а не «понимание смысла».
